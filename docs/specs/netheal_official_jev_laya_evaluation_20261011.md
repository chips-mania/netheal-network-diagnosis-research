## 2. 본 평가 전에 확정할 조건

다음 항목을 원본값·우리 적용값·출처·일치 여부로 기록한 `condition_comparison.md`와 기계 판독 가능한 고정 설정 파일을 작성한다.

- 평가기와 환경의 코드 commit, 컨테이너 image digest, 의존성 버전.
- solver 구현, 시스템 지시문, 최초 과제, 관측/히스토리 전달, 도구 목록 및 인자 스키마.
- 시나리오 TOML, 토폴로지·장비 수·장애 종류/강도·정상 및 복합 장애 포함 여부.
- 평가 snapshot과 해시, episode seed, scenario fingerprint, 에피소드 수와 순서.
- 행동/도구 호출 제한, 시간 제한, 동시성, API/에피소드 재시도 및 실패 처리.
- 힌트 제공 여부와 생성 방식. 원본이 다른 LLM의 힌트를 요구하면 무단으로 API를 추가 호출하거나 힌트를 제거하고 동일 조건이라고 쓰지 않는다. 공개된 고정 힌트 재사용 가능성과 차이를 기록한다.
- 진단 성공 및 위치 동등성 기준, macro-F1 정의, 미완료/오류의 분모 처리와 집계 코드.
- Jev 모델 식별자, API/SDK 버전, 호출 옵션, 요금 근거와 최대 호출량·예상 비용. 과거 1.13.0과 동일하다고 가정하지 않는다.

원본 snapshot이 확보되면 같은 사례를 사용한다. seed만 있으면 코드/난수 생성과 fingerprint까지 확인한다. 복원할 수 없는 핵심 조건은 미확인으로 남기고, 동등성 또는 모델 우열을 단정하지 않는다. 대체 설정은 본 평가 전에 차이와 이유를 명시한다.

## 3. Jev 연결 원칙

1. NetHeal 평가기와 도구 실행/채점 경로를 유지하고 solver 연결부만 변경한다. 별도 작업 디렉터리/환경을 사용한다.
2. Jev가 공개 관측을 읽고 다음 도구와 인자를 선택하며, 최종 장애 유형·위치를 제출한다. 증거를 미리 전부 모아 주지 않는다.
3. 생성형 설명이나 추론 문장을 요구하지 않는다. 선택 응답을 결정적인 코드로 도구 호출/진단 제출에 변환한다. 별도 LLM 요약기·계획기·전문가 대체 판단을 추가하지 않는다.
4. 후보는 원본 도구 스키마와 공개된 대상 정보에서 만든다. 정답·숨겨진 장애 상태·전문가 추천으로 후보를 선별하지 않는다.
5. 도구/인자 선택을 여러 질문으로 나눠야 한다면 원본 행동 공간을 보존하고 분기 규칙을 고정한다. 모델 예측으로 분기하며 정답으로 분기하지 않는다. 내부 질문 수와 실제 환경 행동 수를 별도 기록한다.
6. 원본 입력의 의미를 보존한다. 불가피한 직렬화, 선택지화, 문맥 제한, 히스토리 처리 차이를 명시한다. 따라서 결과는 우선 '동일 평가 조건의 Jev 에이전트' 비교이며, 어댑터가 다르면 순수 모델 교체 효과라고 주장하지 않는다.

## 4. 실행 순서와 판정

- 원본 결과 JSON을 집계해 대상 Run ID의 표시값을 재확인한다.
- API 없는 모의 응답으로 도구/인자 매핑, 진단 제출, 종료·예산 처리, 비공개 정보 차단을 검증한다.
- 본 평가와 분리된 개발 사례에서 작은 Jev 연결 smoke를 수행한다. 연결 결함 수정과 조건 확정 후 설정·소스·모델 ID를 해시로 동결한다.
- 동결된 구성으로 대상 평가를 1회 실행한다. 본 평가 점수를 보며 프롬프트/후보/조건을 바꾸지 않는다. 장애로 재개하면 완료 에피소드를 보존하고 원본 재시도 규칙에 따른다.
- 원본과 같은 전체 분모의 결과를 우선 보고한다. 실패/오류 사례를 빼서 성공률을 올리지 않는다. 실행 완료·중단·미실행을 구분한다.
- 성공 기준은 특정 목표 정확도 달성이 아니라 **조건 대조, 평가 실행, 원시 기록과 집계 재현 완료**다. Claude 대비 개선 여부는 측정 결과로 판단한다.
- 동일 사례의 원본 진단 결과가 있으면 paired 비교와 불일치 사례를 분석한다. 없으면 집계값 비교만 하고 paired 유의성 주장을 하지 않는다.

기록 지표: 진단 성공률(유형+위치), 유형 정확도/macro-F1, 위치 정확도, 오진·미완료·API 오류, 원본 보상/효율 지표, 도구 호출/반복, 모델 요청 수, 전체 시간과 API 시간, 토큰 usage 및 추정 비용. 시간·비용은 실행 환경 차이를 함께 보고한다.

## 5. LAYA 후속: 8비트 optimizer 우선

Jev 평가 경로를 확보한 뒤 동일한 환경/도구 인터페이스에 LAYA를 연결한다. 기존 학습 모델은 이전 개발 실험의 산출물로 구분한다.

- 먼저 별도 환경에서 **8비트 optimizer로 전체 Encoder+Head 학습**의 실행 가능성을 점검한다. 가중치 전체를 8비트로 바꾸는 것과 optimizer 상태를 8비트로 저장하는 것을 구분한다.
- GTX 1660 SUPER 6GB, RAM 약 16GB에서 라이브러리/Windows 호환성을 확인한다. 기존 환경을 덮어쓰지 않는다. GPU 작업은 하나씩 실행한다.
- FP32 가중치를 출발점으로 microbatch 1, 필요 시 gradient checkpointing을 사용한다. FP16은 기존에 느렸으므로 자동으로 전환하지 않는다.
- 실제 전체 backward와 optimizer step을 여러 차례 실행해 각 Encoder 블록과 Head의 업데이트, 유한한 loss/gradient, GPU peak allocated/reserved, 장치 전체 메모리, RAM, update당 시간, 저장/복원을 검증한다.
- 부족하면 우선 메모리 사용 원인을 기록하고 **LoRA+Head**를 검토한다. rank·적용 모듈·학습 파라미터 수를 실행 전에 확정한다. LoRA를 전체 가중치 미세조정 완료라고 보고하지 않는다.
- 본 학습 데이터는 평가셋과 분리한다. 행동 선택·인자·종료를 학습할 경우 중간 상태 궤적을 포함하고, 사례 수·질문 수·유효 배치·실제 optimizer updates를 함께 기록한다.
- 학습 데이터 크기, 학습률, update 예산, seed, 검증 및 checkpoint 선택 기준은 자원 점검 후 **본 학습과 평가 전에 별도 사전 명세**로 고정한다. 지금은 미확정이며 완료로 쓰지 않는다.
- 평가 사례/정답을 학습 또는 설정 선택에 사용하지 않는다. 공식 평가셋의 과거 사용/중복 여부도 감사한다.
