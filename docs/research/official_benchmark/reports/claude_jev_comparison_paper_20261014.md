# 구조화된 관측 상태를 이용한 JEV 네트워크 장애 진단: NetHeal 공개 Claude 결과와의 비교

**문서 유형:** 실험 논문 초안  
**작성일:** 2026년 10월 14일  
**JEV 평가일:** 2026년 10월 13일  
**평가 범위:** 동일 초기 스냅샷 100개에 대한 공개 Claude 결과와 JEV 단일 실행 비교

## 초록

본 연구는 네트워크 장애 진단 과정에서 누적 도구 실행 이력을 구조화된 관측 상태로 변환해 전달하는 JEV 에이전트의 성능을 평가한다. 원본 도구 결과는 별도로 보존하고, 모델에는 현재 토폴로지, 장치 상태, 누적 진단 증거, 행동 이력, 최신 관측 및 과제 정보를 제공하였다. 변환기는 장애 원인을 추론하거나 의심 대상을 지정하지 않으며, 입력 분할과 여러 판단 점수의 가중평균도 사용하지 않았다. NetHeal 공개 Claude 평가와 동일한 100개 초기 스냅샷을 사용하고 모든 시나리오 fingerprint의 일치를 검증하였다. 장애 유형과 위치를 모두 맞힌 비율은 JEV 48.0%, 공개 Claude 66.0%였다. 성능 저하 장애에서는 JEV가 23/29개, Claude가 17/29개를 맞혔으나 장치 및 링크 장애에서는 Claude의 성능이 높았다. 사례당 평균 실행시간은 JEV 4.45초, Claude 221.72초였다. 기존 원문 이력을 전달한 JEV 실행과 비교하면 보고된 총 입력 토큰은 70.25% 감소했고, 입력 초과 오류는 40건에서 0건으로 줄었다. 실제 JEV 요청 1,946건은 해당 시점까지의 원본 관측으로 재구성한 상태와 모두 일치하였다. 본 결과는 구조화 상태를 이용한 진단 파이프라인의 실행 가능성과 유형별 성능 차이를 보여준다. 공개 Claude는 재실행하지 않았고 입력 형식, 응답 방식 및 실행 환경이 다르므로, 관측된 차이를 모델 자체의 판단 능력이나 속도 차이로 단정할 수 없다.

**주제어:** 네트워크 장애 진단, NetHeal, JEV, Claude, 구조화된 상태 압축, 도구 사용 에이전트

## 1. 서론

네트워크 장애 진단 에이전트는 도구를 선택하고 결과를 관측한 뒤, 추가 측정 또는 최종 진단을 결정한다. 전체 도구 실행 이력을 매번 입력하면 같은 토폴로지와 상태 배열이 반복될 수 있다. 반면 최신값이나 성공 여부만 남기면 지연시간, 손실률, 경로 및 시간에 따른 변화 등 진단에 필요한 증거가 생략될 수 있다.

본 연구는 원본 로그의 보존과 모델 의사결정 입력을 분리한다. 도구 결과는 원문 그대로 저장하되, 모델에는 결정론적 변환기로 생성한 구조화 상태를 제공한다. 이 상태는 관측된 사실과 실행 이력을 누적하며, 장애 원인에 관한 해석을 미리 제공하지 않는다. 따라서 변환기의 역할은 증거 정리이고, 다음 도구와 진단 대상의 선택은 JEV가 수행한다.

연구 질문은 다음과 같다.

1. 구조화 상태를 사용하는 JEV는 동일 초기 사례에서 공개 Claude 기준선과 비교해 어느 수준의 진단 성능을 보이는가?
2. 성능 차이는 장애 유형에 따라 어떻게 달라지는가?
3. 소요시간, 진단 단계 수, 입력 토큰 및 실행 오류는 어떻게 나타나는가?
4. 모델에 전달한 상태가 해당 시점까지의 실제 관측과 일치하는지 검증할 수 있는가?

본 문서는 새로운 Claude 실행이나 독립된 미관측 평가셋을 포함하지 않는다. 연구 범위는 이미 확보한 공개 기준선과 후속 JEV 실행의 기술적 비교이다.

## 2. 실험 방법

### 2.1. 평가 데이터와 기준선

Claude 기준선은 NetHeal 공개 제출 `manikyabard-20260201-100940`의 100개 결과를 사용하였다[1]. 같은 제출의 초기 스냅샷을 JEV 환경에 로드했으며, `snapshot_id`와 `scenario_fingerprint`를 대조해 100/100개의 일치를 확인하였다. 장치 수는 사례당 3–15개이며 전체 장치 수 합계는 798개이다.

| 장애 유형 | 사례 수 | 비율 |
|---|---:|---:|
| 장치 장애 (`device_failure`) | 28 | 28% |
| 링크 장애 (`link_failure`) | 21 | 21% |
| 설정 오류 (`misconfiguration`) | 22 | 22% |
| 성능 저하 (`performance_degradation`) | 29 | 29% |
| 전체 | 100 | 100% |

초기 환경은 같지만 이후 행동과 관측 경로는 에이전트의 선택에 따라 달라진다. 따라서 이 실험은 동일한 도구 결과를 고정하여 재생한 비교가 아니다.

Claude는 AWS Bedrock을 사용하는 공개 에이전트이다. 제출 설정의 모델 식별자는 `${BEDROCK_MODEL_ID}` 변수로 지정되어 있으며, 본 문서에서는 확인되지 않은 Claude 세부 버전을 임의로 명시하지 않는다. 보관된 이미지 digest와 소스 검증으로 원본 시스템 프롬프트 및 요청 구성 코드를 확인했지만, 당시 실제 요청·응답 전문과 토큰 usage는 확보하지 못했다[5, 6].

### 2.2. 도구 환경 및 실행 설정

두 평가 모두 같은 공개 NetHeal 사례와 도구 정의를 기반으로 한다. 사용 가능한 도구는 `list_actions`, `scan_network`, `discover_neighbors`, `ping`, `traceroute`, `check_status`, `check_interfaces`, `submit_diagnosis`이다.

| 항목 | 공개 Claude | 구조화 상태 JEV |
|---|---|---|
| 결과 확보 방식 | 기존 공개 평가 결과 재사용 | 새 API 실행 |
| 모델 정보 | Bedrock Claude; 정확한 모델 ID 미확인 | `jev-1.13.0` |
| 초기 사례 | 공개 스냅샷 100개 | 같은 스냅샷 100개 |
| 환경 단계 제한 | 100 | 100 |
| 사례당 시간 제한 | 1,200초 | 1,200초 |
| 에피소드 동시성 설정 | 5 | 1 |
| 에피소드 재시도 설정 | 최대 10회; 공개 집계의 실제 재시도 0회 | 0회 |
| 모델 입력 | 누적 대화 및 도구 결과 | 하나의 구조화된 관측 상태 |
| 응답 방식 | 자연어 설명 및 native tool calling | 선택형 도구·인자 결정 |
| 실행 환경 | 원본 컨테이너 기반 실행 | Windows 직접 handler 실행 |

JEV는 도구를 고른 뒤 필요한 인자를 순차 선택한다. 도구 호출 한 번에 모델 호출이 여러 번 발생할 수 있으므로, API 호출 수와 환경 단계 수는 구분한다. 유효 인자 후보는 공개 `list_actions` 결과에서 생성하며, 후보 조회 결과도 원본 로그에 보존한다. 이 보조 조회는 진단 증거를 평가하거나 후보 우선순위를 계산하지 않는다.

JEV는 solver turn을 100회로 제한하고, `list_actions`를 제외한 환경 도구 호출은 단계 예산을 소비한다. 반복 행동은 허용하였다. 모든 사례는 동일한 고정 설정으로 평가했으며, 결과에 따른 재실행이나 제외를 수행하지 않았다. 프로토콜, 사례 목록 및 실행 소스 해시는 평가 전에 저장하였다[2].

### 2.3. 구조화된 상태 압축

원본 결과 저장 계층과 모델 입력 계층을 분리하였다. 원본 `tools.jsonl`에는 도구 이름, 인자 및 반환 결과를 저장하고, `helpers.jsonl`에는 유효 후보 조회 결과를 저장한다. 실제 API 요청과 응답도 별도로 보존한다.

모델에 전달하는 정보는 다음과 같이 구성한다.

| 정보 영역 | 보존 내용 | 처리 원칙 |
|---|---|---|
| 과제 문맥 | 목표, 사용자 힌트, 네트워크 크기, 현재 단계, 남은 예산 | 실제 실행 상태에서 갱신 |
| 토폴로지 | 발견 장치, 행렬의 비영 값, 인덱스별 연결 상태 및 변경 기록 | `0`은 미확인으로 취급; 행렬 인덱스를 장치 ID로 추정하지 않음 |
| 장치 상태 | `check_status`의 마지막 실제 반환값과 관측 시각 | 미관측 장치를 정상으로 해석하지 않음 |
| 진단 증거 및 행동 이력 | 도구·인자별 호출 횟수, 측정 버전, 관측 단계 및 시각 | 모든 측정 데이터와 변화 유지 |
| 최신 관측 | 방금 실행한 도구, 인자 및 실제 `action_result` | 원본과 일치하는지 검사 |

간결한 도구 스키마와 원본 에이전트의 시스템 프롬프트도 함께 전달하였다. 진단 증거와 행동 이력은 구현에서 `diagnostic_evidence_and_action_memory`라는 하나의 영역으로 저장한다.

같은 도구와 인자에서 연속된 측정 결과가 같으면 측정 본문을 한 번 저장하고 각 실행의 단계와 시각을 누적한다. 비교 시 관측 시각 필드를 제외한 측정 필드 전체를 대조하며, 수치 또는 다른 반환값이 바뀌면 새 측정 버전을 저장한다. 과거 값으로 되돌아온 경우도 별도 변화로 남긴다. `result_changed`는 해당 도구·인자의 실제 관측 전체를 비교한 결과로 결정한다.

Ping의 지연시간과 손실률, Traceroute의 경로와 홉별 측정값, Interface 반환 데이터 등은 존재하는 원본 필드를 그대로 유지한다. 단순한 `success` 표시로 수치 정보를 대체하지 않는다. 도구 반환값에 이미 포함된 사실은 보존하지만, 변환기가 의심 링크를 지정하거나 장애 원인을 추가 추론하지 않는다.

반복 관측 스냅샷, 해시 기반 RL 상태 배열, 보상 및 `reward_breakdown`, 전체 `valid_actions` 숫자 목록은 모델 상태에서 생략한다. 유효 행동 후보는 해당 선택 질문에서 제공한다. 이 방식은 **의사결정 지향 상태 압축(Decision-Oriented State Compression)**이며, 전체 원본 관측을 모델 입력만으로 복원할 수 있는 엄격한 무손실 압축은 아니다. 원본 로그가 별도로 보존된다는 사실과 모델 입력의 무손실성은 구분한다.

### 2.4. 단일 상태 기반 의사결정

각 선택 질문에는 그 시점의 전체 구조화 상태를 한 번 제공한다. 이력을 여러 부분으로 나누어 각각 점수를 계산하거나 결과를 가중평균하지 않았다. 도구 선택과 인자 선택은 별개 질문으로 순차 실행하지만, 여러 입력에서 얻은 판단 점수를 합성하는 앙상블은 사용하지 않는다.

공식 평가의 장치 수 가중 평균은 결과 집계 방식이며, 모델 행동 선택에서의 점수 가중평균과는 별개이다.

## 3. 평가 지표와 검증

### 3.1. 진단 정확도

주요 지표는 장애 유형과 위치를 모두 맞힌 공동 정답률이다. 사례 수를 \(N\), 공동 진단 성공 여부를 \(y_i\)라고 하면 다음과 같다.

\[
\mathrm{Exact}=\frac{1}{N}\sum_{i=1}^{N}y_i.
\]

공식 가중 성공률은 장치 수 \(n_i\)를 가중치 \(w_i=\max(1,n_i)\)로 사용한다.

\[
\mathrm{WeightedExact}=\frac{\sum_i w_i y_i}{\sum_i w_i}.
\]

추가로 장애 유형만 맞힌 비율, 공식 유형 macro-F1, 장애 유형별 공동 정답률, 동일 사례의 성공 여부 교차표를 보고한다. Macro-F1은 네 장애 유형의 F1을 동일 가중치로 평균한 값이다. 공동 성공 판정에는 원래 NetHeal 평가기와 위치 일치 규칙을 사용하였다[7].

### 3.2. 단계 및 소요시간

환경 단계 수는 단순 평균과 공식 장치 수 가중 평균을 함께 보고한다. 시간은 JEV 에피소드 기록의 `seconds`와 Claude 공개 기록의 `time_used`를 사용하였다. 두 값은 전체 진단 실행 경로의 시간이며, 모델 추론 시간만을 분리한 값은 아니다.

전체 사례 평균 외에 성공 사례, 실패 사례, 두 모델 모두 성공한 동일 사례의 평균도 계산한다. 빠른 오진이 전체 평균 시간을 낮출 수 있기 때문이다. 성공 사례끼리의 비교는 서로 다른 사례 집합일 수 있으므로, 공통 성공 사례 37개를 별도로 제시한다.

100개 시간 합계는 사례별 시간의 합이다. 특히 동시성이 5인 Claude의 시간 합계를 실제 평가 작업의 달력상 경과시간으로 해석하지 않는다. Python 시작, import, 사전 검증 및 사후 감사 시간은 JEV 에피소드 시간에서 제외된다.

### 3.3. 토큰·입력량·실행 안정성

JEV API가 보고한 입력 토큰 합계와 최대값, API 요청 수, HTTP 오류 및 입력 초과 오류를 집계한다. Claude의 실제 usage가 없어 Claude와 JEV의 토큰·비용·모델 호출 수를 직접 비교하지 않는다. 토큰 분석은 기존 원문 입력 JEV 실행과 구조화 상태 JEV 실행의 보조 비교로 한정한다.

같은 구조화 JEV 실행 경로에 대한 원본 history 상태와 실제 구조화 입력의 바이트 합계도 비교한다. 이 비교는 토큰 절감률과 동일하지 않으며, 두 표현의 필드 구성 차이를 포함한다.

### 3.4. 관측 일치 및 시간적 인과성 검증

## 5. 논의

### 5.1. 구조화 상태의 실행 효과

관측 결과는 구조화 상태를 통해 입력을 줄이면서도 도구 측정값과 변화 이력을 검증 가능한 형태로 전달할 수 있음을 보여준다. 원문 입력 JEV에서 발생했던 입력 초과 오류가 이번 실행에서는 없었으며, 모델이 더 많은 선택 요청을 수행하면서도 보고 입력 토큰 총량은 줄었다.

다만 더 짧은 입력, 보상 및 RL 배열의 생략, 정보의 재배치, 행동 경로의 변화가 동시에 발생했다. 따라서 결과를 구조화 압축 하나의 독립 효과로 설명할 수 없다. 엄격한 효과 분리를 위해서는 동일 관측 경로를 고정한 입력 비교와 새로운 독립 평가가 필요하다.

### 5.2. 전체 정확도와 유형별 성능의 차이

전체 공동 정답률은 공개 Claude가 높았다. 특히 장치 및 링크 장애에서 차이가 컸다. JEV가 성능 저하 사례에서 더 높은 성공률을 보인 사실은 별도로 보고할 가치가 있지만, 이것이 수치 증거 보존 때문인지, 모델의 유형별 성향 때문인지, 선택형 인터페이스 또는 행동 경로 때문인지는 이번 실험으로 판단할 수 없다.

유형 정답률과 공동 정답률 사이에는 Claude 8%p, JEV 16%p의 차이가 있다. 유형을 맞힌 뒤 위치 선택까지 정확하게 수행하는 과정이 JEV의 추가 개선 대상임을 시사한다. 구체적 원인 진단에는 사례별 행동 및 측정 로그 분석이 필요하다.

### 5.3. 효율 지표의 해석

시간과 단계의 감소는 정답률과 함께 평가해야 한다. 전체 평균만으로는 적은 관측 후 제출한 오진과 충분한 증거를 수집한 정답을 구분하기 어렵다. 본 문서는 공통 성공 사례의 시간과 단계도 제시했으나, 이 역시 실행 환경 차이를 제거하지는 못한다.

원본 로그가 보존되어 있어 진단 도구 반복, 증거 수집, 잘못된 위치 선택 등을 사후 분석할 수 있다. 모델이 읽는 입력을 압축하더라도 재현성과 분석 가능성을 유지하는 것이 이번 설계의 실용적 장점이다.

## 6. 한계 및 후속 연구

1. **입력 및 인터페이스 차이:** Claude는 누적 대화와 native tool calling을, JEV는 구조화 상태와 순차 선택형 응답을 사용하였다. 같은 StructuredState를 두 모델에 제공한 통제 실험은 아니다.
2. **실행 환경 및 시점 차이:** Claude는 기존 공개 실행, JEV는 2026년 10월 실행이며 API 제공자, 운영체제 및 동시성이 다르다. 시간 차이의 원인을 분리할 수 없다.
3. **단일 실행과 평가셋 재사용:** 100개는 서로 다른 사례이지만, 모델별 반복 실행은 수행하지 않았다. 이미 관측한 사례의 후속 실험이므로 독립된 새로운 평가셋에서의 성능을 입증하지 않는다. 통계적 유의성과 일반화 성능을 주장하지 않는다.
4. **엄격한 무손실성 부재:** 원본 전체가 보존되어도 모델 입력은 일부 관측 필드를 생략한다. 의사결정 지향 압축으로 명시해야 한다.
5. **Claude 관측 자료의 제한:** 실제 대화 전문, 입력·출력 토큰, 모델 호출 수 및 비용을 확보하지 못했다. 정확한 Claude 모델 ID도 이 문서의 확인 범위에서 확정하지 않았다.
6. **토큰 비교의 혼합 요인:** 두 JEV 실행의 행동 경로가 달라 총 토큰 감소를 순수한 압축 효과로 해석할 수 없다. 실패 요청의 usage 부재도 집계에 영향을 준다.

후속 연구에서는 같은 구조화 상태를 Claude와 JEV에 제공하는 비교, 전체 이력·무손실 표현·의사결정 지향 상태를 나눈 비교, 동일 관측 경로의 입력량 측정, 새로운 평가셋 및 반복 실행을 수행할 필요가 있다. 공통 성공 사례뿐 아니라 전체 사례에서 정답률과 지연의 관계도 함께 평가하는 것이 바람직하다.

## 7. 결론

동일한 NetHeal 초기 사례 100개에서 구조화 상태 JEV는 공동 진단 정답률 48%, 공개 Claude는 66%를 기록하였다. JEV는 성능 저하 사례에서 더 높은 성공률을 보였고, 기록된 사례당 평균 시간은 4.45초였다. 기존 원문 JEV 대비 보고 입력 토큰은 70.25% 감소했으며 입력 초과 오류는 0건이었다.

원본 로그를 보존하면서 관측 사실을 구조화하여 제공하는 방식은 입력 안정성과 사후 검증을 확보하는 데 유효하였다. 그러나 전체 정답률과 유형별 성능의 차이, 입력 및 실행 조건의 차이가 남아 있으므로, 이번 결과만으로 JEV가 Claude의 판단 역할을 전반적으로 대체한다고 결론내릴 수 없다. 동일 입력 조건과 독립 평가를 통한 추가 검증이 필요하다.
