# 한도 초과 두 사례의 입력 표현 비교

2026-10-13. 사용자 지정 범위에 따라 초기 v2의 한도 초과 사례 중 ID 정렬 순 첫 두 사례만 보고한다. 중단 전 여섯 사례가 측정되었으나 나머지는 본 비교에서 제외하고 원시 기록만 보존했다. 범위 확정 후 추가 API 호출은 없었다.

각 사례에서 과거 HTTP 400이 발생했던 요청 하나를 고정하고 세 표현을 실제 `jev-1.13.0` API에 전송했다. 질문·선택지·순서와 모든 관측 이력은 유지했다. 24KB 가드와 분할은 적용하지 않았다. 전체 에피소드나 진단 정확도 평가는 아니다.

| 입력 | 사례 0283628d… (기존 요청 20) | 사례 0307b569… (기존 요청 18) |
|---|---:|---:|
| 기존 원문 | HTTP 400, 토큰 수 미반환 | HTTP 400, 토큰 수 미반환 |
| 기존 압축 | 6,451토큰, HTTP 200 | 6,300토큰, HTTP 200 |
| 구조 변경 원문 | 30,021토큰, HTTP 200 | 29,648토큰, HTTP 200 |

위 토큰은 성공 응답의 `usage.input_tokens` 값이다. 실패 응답은 `max_tokens_exceeded`만 반환해 정확한 초과 토큰 수는 알 수 없다.

| 상태 표현 UTF-8 크기 | 사례 0283628d… | 사례 0307b569… |
|---|---:|---:|
| 기존 원문 | 42,481바이트 | 41,363바이트 |
| 기존 압축 | 15,249바이트 | 14,860바이트 |
| 구조 변경 원문 | 40,008바이트 | 38,890바이트 |

바이트는 비교용 상태 문자열 크기이며 서버 토큰 수나 전체 HTTP 본문 크기가 아니다. 기존 원문 객체는 로컬에서 공백 없는 JSON으로 직렬화해 크기를 계산했다.

기존 원문은 당시 request body의 state 객체를 그대로 사용했다. 기존 압축은 v4 자체 무손실 코덱이 출력한 문자열이다. 구조 변경은 앞선 첫 사례 실험과 동일하게 도구 이름·설명·inputSchema만 남기고 schema title 주석을 제거한 뒤 일반 JSON 문자열로 전송했다. 따라서 도구 정의 간소화와 객체→문자열 전송 변화가 함께 포함되어 있으며, 통과 원인을 도구 설명 삭제만의 효과로 단정할 수 없다. Claude 시스템 프롬프트를 그대로 적용한 조건도 아니다.

두 사례 모두 압축 없이 구조 변경만으로 단일 요청이 수용됐다. 기존 24KB 가드는 이 입력을 분할했겠지만 실제 API는 수용했다. 기존 압축은 구조 변경 입력 대비 보고 토큰을 각각 약 78.5%, 78.8% 줄였다. 그러나 수용 및 토큰 감소가 진단 성능 보존을 입증하지는 않으며, 다른 긴 사례도 모두 수용된다고 일반화할 수 없다.
